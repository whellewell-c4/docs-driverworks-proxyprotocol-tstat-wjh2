    Introduction

    This documentation includes content that details the functions that make up the Thermostat Control Proxy which is supported in the DriverWorks Software Development Kit.

    Proxies (Commands)

    A proxy driver is an interface to the Control4 system for a set of devices that share common functionality. For instance, most Thermostats have common controls such as INCREASE SET POINT, DECREASE SET POINT and SET PRESET.  The Thermostat proxy allows for a common user interface to control all Thermostats.  The Control4 system (Director) sends information to and receives information from the proxy drivers.  The proxy drivers send information to and receives information from the protocol drivers. Remember, your DriverWorks driver interacts with the proxy driver which then interacts with the system.  As a driver developer you will be relying on this proxy to provide status (notification) to the Control4 system for the device you are controlling.  You will also receive commands from the system that you will act on to control the device.  These commands and notifications are at the heart of what you will be implementing in your driver.  Essentially your driver is becoming the go-between from the Control4 system and your device with the proxy driver giving structure to the commands and notifications which you will be implementing. Your driver can facilitate communications with multiple types of proxies for a single device. As an example, a Security System driver will utilize both the Security proxy and the Contacts proxy. These additional proxies are configured in the <connections> section of the .c4z.

    Protocol (Notifications)

    Two similar devices may have the same functionality but utilize a very different command set.  A protocol driver provides the device-specific information needed to communicate with the Control4 system.  In the case of DriverWorks, the DriverWorks driver is the protocol driver.  When combined with the device-specific.c4Z file it provides the custom code necessary to implement the 2-way device driver. In the case of DriverWorks, the DriverWorks driver is the protocol driver. When combined with the device-specific.c4Z file it provides the custom code necessary to implement the 2-way device driver.

    Thermostat Capabilities

    THERMOSTAT CAPABILITIES

    The following Capabilities are supported with the Thermostat Proxy.

    Note the reference to the Dynamic Capabilities Changed notification in many of the capabilities defined below. Using the Dynamic Capabilities notify is a way for a protocol driver to send updates about some capabilities that can be changed when settings change on the hardware.  An example would be a thermostat that now includes a humidifier. The thermostat would need to tell the proxy it can now do humidification. The  <can_humidify></can_humidify> capability is designated as a capability that can be changed using Dynamic Capabilities Changed. The capability can be passed as a parameter in the notify to update the thermostat proxy regarding humidification ability.

    Additionally, please see the Samples folder delivered in this SDK for additional Thermostat (V2) code examples.

    can_calibrate

    Indicates if the device is capable of calibrating itself. Enables the SET_CALIBRATION command. Valid values: True/False.

    can_change_scale

    Boolean to enable/disable Navigator UIs and ComposerPro from being able to change the scale of the hardware. Valid values: True/False. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    can_cool

    Indicates if this thermostat supports cooling and indicates to UIs and Programming that the device could execute this functionality. Valid values: True/False. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    can_dehumidify

    Boolean to enable/disable can_dehumidity capability, if the device supports this feature, default is True. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification. This is older functionality that indicated to UI's and Programming that the device could execute this functionality.  However, their limitation is that they do not take into account if the current HVAC mode supported them.  HVAC Modes replaced their functionality, but older drivers still use them and they do work. Control4 recommends the use of HVAC Modes now and that this capability be set to false in the driver's configuration file.

    can_do_auto

    Indicates if this thermostat can automatically switch from heat to cool and indicates to UIs and Programming that the device could execute this functionality. If the device can deadband enforcement, it will be done on the UIs as specified with the deadband capabilities. Valid values: True/False. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    can_fixed_schedule_and_presets

    Introduced in 4.3.0. Indicates support for both the legacy schedule plus presets. When <can_fixed_schedule_and_presets> is true then <can_preset> and <can_preset_schedule> should be set to false. This capability allows the driver to use the legacy scheduler along with supporting presets. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    can_heat

    Indicates if this thermostat supports heating and indicates to UIs and Programming that the device could execute this functionality. Valid values: True/False. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    can_humidify

    Boolean to enable/disable can_humidity capability, if the device supports this feature, default is True. It indicates to UIs and Programming that the device could execute this functionality. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    can_inc_dec_setpoints

    Boolean indicating if the device has internal commands to increment and decrement both heat and cool set points independently. If false the proxy will take the current setpoint and +/- 1 (or the resolution) and send a DYNAMIC_CAPABILITIES_CHANGED  command with the new setpoint value, which could potentially send 81 three times if someone did programming of Increment Setpoint and the current setpoint was 80, rather than sending 83 as someone might expect from Composer Programming of 3 increment commands without a sleep between that provides enough time for the hardware to set each increment and return the new setpoint to director before the next Increment occurs.

    can_lock_buttons

    Indicates if the buttons on the TSTAT can be locked out to prevent changes. Valid values: True/False.

    can_lock_screen

    Introduced in 4.3.0. Indicates if the screen on the thermostat device is able to be locked. The modes that are supported are provided by the <lock_screen_modes> capability. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    lock_screen_modes

    Introduced in 4.3.0. Comma delimited string of possible screen-lock modes. Used with '<can_lock_screen'. For example: Unlocked,Partially Locked,Fully Locked. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    can_preset

    Boolean indicating if the device supports the preset functionality including custom_fields. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    can_preset_schedule

    Boolean indicating if the thermostat will support the SET_EVENTS commands for running presets based on scheduling created in Navigators. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    current_temperature_max_c

    Double indicating the maximum temperature that the thermostat will report in C. Default is 48. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    current_temperature_min_c

    Double indicating the minimum temperature that the thermostat will report in C. Default is -40. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    current_temperature_max_f

    Double indicating the maximum temperature that the thermostat will report in F. Default is 120. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    current_temperature_min_f

    Double indicating the minimum temperature that the thermostat will report in F. Default is -40. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    current_temperature_resolution_c

    Double indicating the increments that the temperature will follow, such as .1, .5, 1, 2, 5, etc. Default is 1. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED notification.

    current_temperature_resolution_f

    Double indicating the increments that the temperature will follow, such as .2, .5, 1, 2, 5, etc. Default is 1. Note .2 is the lowest F resolution supported. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    fan_modes

    This is a comma delimited list of possible fan modes this thermostat supports. For example: Auto, Low, Medium, High with no spaces after the comma. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    fan_states

    This is a comma delimited list of all the possible states that the HVAC system fan supports. For example: Off, On, Low, Med, Circulate with no spaces after the commas. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    has_humidity

    Boolean indicating if the device can report the current humidity. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    has_extras

    Boolean indicating if the device has extras commands support. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    has_connection_status

    Boolean indicating if the device reports online/offline status of the hardware device, this is often forgotten about but very important to implement in new protocol drivers drivers.

    has_outdoor_temperature

    Boolean indicating if the device can provide an outdoor temperature. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    has_remote_sensor

    Indicates if this thermostat has a remote sensor. Valid values: True/False.

    has_single_setpoint

    Boolean indicating if the device is single setpoint.  can_heat, can_cool and can_auto should be set to false if this option is used. It indicates to UIs and Programming that the device could execute this functionality. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    has_temperature

    Boolean indicating if the device can provide a temperature of the thermostat/room. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    has_vacation_mode

    Indicates if this thermostat supports vacation mode Valid values: True/False The capability has_vacation_mode must be set to true for the vacation commands and notifications to be executed. Preset Scheduling and Vacation Mode are mutually exclusive and drivers should really use Preset Scheduling to accomplish what Vacation Mode has done in the past.

    hold_modes

    This is a comma delimited list of the possible hold modes this thermostat supports. Valid values include: Off, 2 Hours, Until Next, Permanent with no spaces after the commas. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    hold_until_mode

    Introduced in 4.3.0. Controls whether Hold Until uses time semantics or date,time semantics. The default is date,time. Some thermostats only supports setting the hold until mode within a 24 hour period and only supplies the time. If this is the case then set <hold_until_mode> to "time".

    hold_until_resolution

    Introduced in 4.3.0. Minute resolution used for Hold Until rounding and UI input behavior. Double indicating the increments that the hold_until will follow, such as 1, .5, 10 etc. Default is 5.

    humidity_modes

    A comma separated list of all the modes the device supports. For example: "Off,Humidify,Dehumidify,Auto" with no spaces after the commas. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    humidity_states

    A comma separated list of all the modes the device supports. Usually something like "Off,Humidifying,Dehumidifying", with no spaces after the commas.

    hvac_modes

    A comma separated list of all the modes the device supports. For example: "Off,Heat,Cool", with no spaces after the commas.

    hvac_states

    This is a comma delimited list that represents all of the possible states that the HVAC system supports. For example: Off, Heat, Cool, Heating, Stage 1 Cool, etc with no spaces after the commas

    outdoor_temperature_resolution_c

    Double indicating the increments that the temperature will follow, such as .2, .5, 1, 2, 5, etc. Default is 1. Note that .2 is the lowest C resolution supported. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    outdoor_temperature_resolution_f

    Double indicating the increments that the temperature will follow, such as .2, .5, 1, 2, 5, etc. Default is 1. Note .2 is the lowest F resolution supported. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    preset_fields

    XML of fields for settings that are potentially unique to the protocol driver, yet will be displayed in the UI during the creation or modification of presets for scheduling. This capability can be changed through a DYNAMIC_CAPABILITIES_CHANGED  notification.

    scheduling

    A boolean indicating if the device supports a programmed schedule. If it is true, it should have a schedule_default entry in the capabilities section in the driver.xml file. Mutually exclusive to Preset Scheduling unless can_fixed_schedule_and_presets is true. In 4.3.0, scheduling and schedule_default can be handled dynamically. If either capability is missing from the static capability set, thermostatV2 proxy treats it through the dynamic capability flow. If scheduling is true and the driver is not providing schedule_default through that dynamic flow, the driver should provide a schedule_default block in driver.xml.

    schedule_default

    An XML block indicating the default schedule for the device. Legacy scheduling is mutually exclusive to preset scheduling unless can_fixed_schedule_and_presets is true which was introduced in 4.3.0. In 4.3.0, scheduling and schedule_default can be handled dynamically. If either capability is missing from the static capability set, thermostatV2 proxy treats it through the dynamic capability flow. If scheduling is true and the driver is not providing schedule_default through that dynamic flow, the driver should provide a schedule_default block in driver.xml. See the example below.

    <schedule_default>
    <schedule_day_info Entries = "6" DefaultHeat = "200" DefaultCool = "278">
        <schedule_entry Name = "Wake" Time = "360" Enabled = "True" CanChangeName="False" CanDelete="False"/>
        <schedule_entry Name = "Leave" Time = "480" Enabled = "True" CanChangeName="False" CanDelete="False"/>
        <schedule_entry Name = "Return" Time = "1080" Enabled = "True" CanChangeName="False" CanDelete="False"/>
        <schedule_entry Name = "Sleep" Time = "1320" Enabled = "True" CanChangeName="False" CanDelete="False"/>
        <schedule_entry Name = "Custom 1" Time = "1380" Enabled = "False" CanChangeName="True" CanDelete="True"/>
        <schedule_entry Name = "Custom 2" Time = "1380" Enabled = "False" CanChangeName="True" CanDelete="True"/>
    </schedule_day_info>
</schedule_default>

    function SetDefaultSchedule()
    for dayIndex = 0, 6 do
        for _, entry in ipairs(DEFAULT_SCHEDULE_ENTRIES) do
            SetScheduleEntry(
                dayIndex,
                entry.EntryIndex,
                entry.TimeHour,
                entry.TimeMinute,
                entry.Enabled,
                entry.HeatSetpoint,
                entry.CoolSetpoint,
                entry.Scale,

    DYNAMIC_CAPABILITIES_CHANGED

    Dynamic Capabilities is a way for a protocol driver to send updates about some thermostat capabilities that can be changed when settings change on the hardware.  An example would be a thermostat that has a humidifier added and would need to tell the proxy it can now do humidification as well as what the min, max, resolution and other changes are for the setpoint. 

    There are two types of capabilities, static and dynamic.

    Static capabilities are defined in the <capabilities> section of the driver's driver.xml file and are immutable. For a complete list of Thermostat capabilities, please see the Thermostat Proxy Capabilities section.

    Dynamic capabilities, as discussed in this section, are updated by the driver through the C4:SendToProxy() command. See the Lua Example below. A Lua table needs to be created defining the parameter name and it's value. Dynamic capabilities are not required to be in the driver.xml file. If it is not included it will initialize with the default value and can be updated at any time by the driver. If the thermostat device does not support changing the configuration then it is recommended it be used as a static capability. When a proxy receives a FORCE_INFO notification, it re-sends the current scale, temperature, HVAC mode, fan mode, hold mode, HVAC state, fan state, and heat/cool setpoints back to the UI so the display stays synchronized without requiring a separate variable-specific notification.

    Name

    FORCE_INFO ()

    Parameter Type Default Capability Description
    none None N/A N/A This notification has no payload. It forces the proxy to refresh current information back to the UI.

    Lua example

    local Params = {}

C4:SendToProxy(bindingID, "FORCE_INFO", Params, "NOTIFY")

-- if using the template code you can use SendNotify
--SendNotify("FORCE_INFO", Params, BindingID)

    What this refreshes

    The proxy uses FORCE_INFO to push the most recent values for the following items back to the UI:

    • scale
    • current temperature
    • HVAC mode
    • fan mode
    • hold mode
    • HVAC state
    • fan state
    • heat setpoint
    • cool setpoint
    • display temperature values

    This is a refresh trigger, not a state-change command. It does not require any parameters and does not update the target device; it simply re-sends the current data from the proxy to the UI.

    Usage Note

    This string may or may not have multiple message segments. If it does, the message segments are delimited by a \n (newlines). Some protocol drivers such as the c4-therm support up to 4 lines of messages. Most UI's scroll these \n delimited messages right to left in a marquee style.

    Parameter Type Description
    FAHRENHEIT LEVEL Optional. Single setpoint in Fahrenheit.
    CELSIUS LEVEL Optional. Single setpoint in Celsius.

    Notes

    • At least one temperature parameter must be supplied.
    • The proxy clamps the requested value to the thermostat’s supported single-setpoint range and resolution.
    • If the thermostat supports both Fahrenheit and Celsius, the proxy accepts whichever scale is provided and converts as needed.
    • This command is used for thermostats that expose a single active setpoint rather than separate heat/cool setpoints.

    Command Sent to Protocol Driver

    SET_SETPOINT_SINGLE - sends the single setpoint value to the protocol driver.

    Returns

    None

    UPDATE_SCHEDULE_ENTRY_NAME

    New in 4.3.0.

    Parameters

    • ENTRY_INDEX — required; zero-based index of the schedule entry within each day.
    • NEW_NAME — required; the replacement name to apply to the entry.

    Notes

    • This command applies to all days in the week at the specified ENTRY_INDEX.
    • It does not use DAY_INDEX; the proxy loops through every day and updates each matching entry.
    • The target index must be valid for the thermostat’s GetEntriesPerDay() range.
    • Before renaming any day, the proxy validates every day in the week. If any entry at that index is not re-nameable, the command is rejected and no rename is applied.

    Proxy behavior after completion

    • The proxy checks that the schedule exists and that ENTRY_INDEX is in range.
    • It verifies that NEW_NAME is present.
    • It then loops through all 7 days and calls SetEntryName(newName) on each matching entry that is allowed to be renamed.
    • For each day, it sends the update to the protocol driver using the per-day DAY_INDEX, ENTRY_INDEX, and ENTRY_NAME values.

    Command sent to the protocol driver

    • UPDATE_SCHEDULE_ENTRY_NAME
    • Payload includes:
      • DAY_INDEX
      • ENTRY_INDEX
      • ENTRY_NAME

    This is sent once per affected day, not as a single all-days command.

    Returns

    None
